DOOFINDER ACADEMY — STYLE GUIDE
(distilled from Module 1, Section 1 — use this as the reference when redoing any other section)
================================================================================

1. PAGE / LESSON STRUCTURE
--------------------------------------------------------------------------------
- Every lesson's theory is built from `blocks: [...]`. A block WITHOUT a
  `heading` is just a continuation of the previous block's prose — it must
  never sit in its own block if the block before it is also headless.
  RULE: merge any block that has no `heading` into whichever block came
  right before it. Only blocks that open with a `heading` (a new subtopic)
  get their own `.theory-block` div. This avoids the "double gap" bug
  (each block wrapper has `margin-top: 22px`; two headless blocks in a row
  stack that margin on top of a normal paragraph margin and create a gap
  that looks like a mistake).
- When a lesson covers more than one named subtopic and one of them
  deserves to be read on its own (e.g. "Create a Search Engine" inside
  "Installing Doofinder", or "The Product Data Feed" / "Field Name Mapping"
  inside "Indices and the Data Feed"), mark that block with
  `pageBreak: true` (in addition to its `heading`). This splits the lesson
  into sub-pages behind a "Continue →" button instead of one long scroll.
  Every block after a `pageBreak` block belongs to that same new page,
  until the next `pageBreak`.
- Intro copy for a set of steps gets ONE short framing sentence before the
  list (e.g. "Once an account is created on Doofinder's website, getting it
  live on a site consists of a guided flow through four steps.") — don't
  also repeat that framing right before the list AND have a redundant lead.
- If a list of steps will only make full sense once the learner sees it
  used in the final exercise, say so in ONE plain sentence after the list,
  phrased positively: "This flow will become clearer once you see it
  applied in this section's final exercise." Never phrase this as an
  apology ("it's normal to feel confused").
- Forward references to content covered elsewhere ALWAYS say
  "later in the course" — NEVER name a specific module or section number.
  ("...will be covered in more detail later in the course.")

1b. THEORY LAYOUT INSIDE A LESSON (reference: Module 1 Section 2,
    "Results Preview" and its "Stemming and Character Cleaning" sub-page)
--------------------------------------------------------------------------------
Every lesson's theory is laid out as short, scannable sub-topics instead of
one long run of paragraphs:
- Keep the `lead` as the one-sentence framing at the top (or, if the lesson
  opens with a diagram, it can live as the first paragraph of the
  note beside the diagram).
- Inside a block, split the content with <h3> sub-headings, one per
  sub-topic (e.g. "What It Shows", "Score", "Query Types", "In Practice").
  <h2> stays reserved for the block `heading` (it drives the doc-links
  scroll-spy); <h3> is purely visual.
- Anything that is naturally a list of "item → meaning / example" becomes a
  `<table class="theory-table">`: query types (type | when | example),
  score parts (value | what it means), selector types, feed fields,
  formats, wildcard patterns (pattern | matches | doesn't match), boosting
  values, Exact/Broad Match, AND/OR conditions, synonym types, form fields,
  Add/Replace options... Put code-like values in <code>, labels in <strong>.
- The single most important rule or gotcha of a sub-topic goes in ONE
  `<p class="theory-callout">` (e.g. the match_and → match_or → fuzzy
  fallback order, "Replace can't be undone", "only one default banner").
  Don't stack several callouts in a row.
- Images sit INSIDE the flowing text, magazine/newspaper-style: a float
  (`<figure class="lesson-figure lesson-figure-left|right" style="width: NNNpx;">`)
  placed right before the paragraphs it goes with, so the text wraps around
  it and keeps flowing underneath once it's past the image — never a
  two-column split, which leaves an empty gap under the shorter column.
  Carousels do the same with `install-step-carousel float-left`; an SVG
  diagram with `<div class="diagram-figure lesson-figure-left">`.
  Alternate left/right between consecutive images for a magazine feel.
  When two image + paragraph pairs follow each other (e.g. two
  configurations being compared), put a `<div style="clear: both;"></div>`
  between the pairs so the second image never sits beside the first one,
  alternate the sides (first left, second right), and shrink the images
  (~300px) so each one is roughly as tall as the paragraph next to it.
  This applies to wide screenshots too: NEVER put an image at full width
  (width: 100%) — even a very wide one floats to one side at ~420-520px
  with the text wrapping around it (it can still be enlarged via zoom).
  <h3> sub-headings do NOT clear floats (the next sub-topic flows up beside
  the image too) and callouts don't either (they sit beside the image,
  narrowed, via `display: flow-root`); tables DO clear, so they're never
  squeezed beside an image. See section 2b for the full layout rules. The zoom badge must sit inside a `position: relative`
  wrapper (`.lesson-figure` and `.diagram-figure` both are).
- Don't force structure: a plain step list or two short paragraphs can
  stay as they are.
- Concept examples (stemming, character cleaning, query types...) are
  generic, simple and in English (run/runs/running, café/cafe,
  résumé/resume, "red t-shirt") — NOT taken from the Doostride feeds or
  products, unless the lesson is explicitly about Doostride's own data
  (Results Preview screenshots, final exercise). Any stem/token shown must
  be verified with a real stemmer (Snowball English), not guessed.

RESTRUCTURING AN EXISTING LESSON — NEVER REMOVE CONTENT
- When converting an existing lesson to this layout, change ONLY the
  structure. Every concept, example, number, limit, product name and caveat
  must survive — keep the original wording wherever it fits, and only
  rephrase minimally to fit a table cell. Shortening or "simplifying" is a
  separate request and needs to be asked for explicitly.
- Verify it: split the old text (git HEAD) into clauses, list every clause
  not present verbatim in the new text, and check each one by hand until
  its concept is found in the new version. Also check the word count
  didn't drop noticeably and every image/src is still there.

2. IMAGES
--------------------------------------------------------------------------------
- A single illustrative image inside theory copy uses:
    <figure class="lesson-figure lesson-figure-left|lesson-figure-right" style="width: NNNpx;">
      <img src="img/....png" alt="<describes exactly what the screenshot shows>" data-action="zoom-image">
      <p class="example-caption" title="Click the image to enlarge it" aria-label="Click the image to enlarge it">
        <svg viewBox="0 0 16 16" width="12" height="12" fill="none" stroke="currentColor" stroke-width="1.6">
          <circle cx="6.5" cy="6.5" r="4.5"></circle><line x1="10" y1="10" x2="14" y2="14" stroke-linecap="round"></line>
        </svg>
      </p>
    </figure>
  The default width is 320px — override with an inline `style="width: NNNpx; max-width: 55%;"`
  case by case so the image's height roughly matches the height of the text
  it floats beside (neither the text nor the image should trail far below
  the other — check in the browser and adjust the width up or down).
- NEVER use a text hint like "Click the image/an image to enlarge it" —
  always the magnifying-glass badge above (`.example-caption` in data files,
  or the `ZOOM_BADGE` constant in app.js for anything generated in JS).
- A sequence of screenshots that shows one flow step by step (e.g. the 4
  screens of creating a Store → Search Engine → connecting the script)
  becomes a single-image-at-a-time carousel, not a stack of images:
    <div class="install-step-carousel">
      <img ... class="is-active"> <img ...> <img ...> ...
      <button type="button" class="carousel-next-btn" data-action="carousel-next">Next step →</button>
    </div>
  Add `float-left` to the wrapper class when it needs to sit beside running
  text (`.install-step-carousel.float-left` is fixed at 500px/400px tall).
- A set of images the learner must compare and pick ONE of as the answer
  (e.g. 3 possible mapping configs) uses the existing image-choice thumbnail
  row (`.image-choice-row` / `.image-choice-thumb`), each thumb carrying an
  orange pill label ("Option A", "Option B"...) — see section 4 below.
- A downloadable file that has a visual shape worth previewing (a data
  feed, a spreadsheet) gets its own preview image (a real screenshot of the
  file's first rows rendered as a small table) plus a download button,
  using the feed-preview-card pattern — see section 4.
- When several of these preview cards sit side by side, wrap them in
  `.feed-preview-grid` (flex row, wraps on narrow screens, NOT a column).

2b. LESSON LAYOUT — REFERENCE: Module 1 Section 3, "Grouping Product Variants"
--------------------------------------------------------------------------------
This lesson's page structure, text/image arrangement and image sizes are the
approved model for every lesson and exercise. Relaying out a page changes
ONLY layout and images — never the content (verify with a text diff, below).
- FIGURES: every image is a floated
    <figure class="lesson-figure lesson-figure-left|right" style="width: NNNpx; max-width: 55%;">
  with the zoom badge, placed right BEFORE the paragraph(s) it goes with.
  Always add `max-width: 55%` so on narrower screens the text beside it never
  shrinks to a 2-3 word column. Sides alternate left/right.
- SIZES: tune the width so the image's rendered height ≈ the height of the
  text beside it. Rough guide: wide/short images (feed tables) 440-500px;
  Search Layer / Admin Panel screenshots 300-420px.
- NO EMPTY GAPS:
  - Never put `<div style="clear: both;"></div>` right before an <h3> if it
    leaves empty space beside an image: let the new sub-topic (h3 + text)
    start beside the image.
  - A `clear` is only for two consecutive image + paragraph pairs, so the
    second image doesn't sit next to the first.
  - Never leave a tall image beside one short line: move the figure one or
    two paragraphs earlier/later WITHIN the same sub-topic, next to a longer
    run of text (moving a figure is fine; moving text is not).
  - `.theory-callout` sits beside a floated image (CSS: `display:
    flow-root`, no `clear`), narrowed so it doesn't overlap it — use this to
    fill the space instead of leaving it empty.
- FILLING A GAP (image noticeably taller than the text beside it, checked
  at 1920 / 1400 / 1200 wide), in this order of preference:
  1. Move the figure one or two paragraphs earlier/later within the same
     sub-topic, next to a longer run of text.
  2. Remove a `clear` that isn't needed (never leave two images side by
     side).
  3. Adjust the figure width (keeping `max-width: 55%`) without making it
     unreadable.
  4. Crop the image's empty margins so it's shorter.
  5. Only then, add or extend ONE sentence that is fully consistent with
     the lesson: describe what the image shows (e.g. "each result with its
     image, title and price, and the Brands filter counts two Ray-Ban
     products and one Gucci product"), or restate a fact the lesson already
     gives elsewhere. Never invent behaviour, numbers, limits or steps, never
     add generic filler, never distort the context. Quizzes are not touched.
- IMAGES:
  - Crop tight: no big empty white/blank areas (crop with PIL). A
    screenshot with a huge empty margin renders tiny and wastes space.
  - Generated images are rendered at 2x (device scale factor 2) so they stay
    crisp when zoomed.
  - Feed/table images are generated PNGs in one style (see
    img/grouping-feed-group-id.png): white bg, header row (243,244,248), bold
    dark header, DejaVu Sans 13px at 2x, alternating row tint (247,248,251),
    thin row lines (226,228,236). The data must match the text and the
    downloadable CSV exactly.
  - Search Layer examples (e.g. img/grouping-layer-ungrouped.png /
    -grouped.png) are an HTML mock of the Search Layer (search bar, filter
    column on the left, "N results found", product cards) screenshotted with
    headless Chrome at 2x and cropped to the content. Product photos come
    from real sources (e.g. the support article's images), never invented.
    Show only the filters relevant to the point being made.
  - Use an animated GIF instead of a still image when the point is a
    sequence of clicks in one screen (e.g. "Copy Settings to…" → pick the
    Search Engine → Apply → Copy settings mode → Yes, apply; typing and
    adding search terms). Take the GIF from the support article, crop it
    to the useful area with ffmpeg (crop + palettegen/paletteuse, keeps the
    file small), and float it like any figure with the pause/play control:
    <figure class="lesson-figure lesson-figure-right gif-image" style="...">
      <img src="img/x.gif" data-base-src="img/x.gif" ... data-action="zoom-image">
      <canvas class="gif-freeze-canvas"></canvas> + gif-toggle-btn + zoom badge
    Keep a still image when the point is one state (a form, a result).
  - A new image is created only when the user asks for it or when the text
    already describes that data/screen and has no image for it — never
    invent content for it.
- EXERCISES: final-exercise steps keep the scenarioImage / scenarioFeed +
  scenario split system (section 6). Only images (crop, crispness) and the
  layout flags (smallMedia / mediumMedia / mediaRight) are tuned; related
  cards (e.g. the three feed previews) must be the same size so none stands
  out and hints at the answer.
  With the 1000px cap, image-choice steps whose thumbnails don't fit beside
  the text use `stacked: true` (images full width, question below) instead
  of a `mediaWidth` that leaves an empty strip or overflows the card. A
  scenarioImage shorter than its text column can use `imgClass:
  "taller-scenario-img"`. A wide screenshot (e.g. a whole Search Layer with
  several results) uses `stackedMedia: true` + `wideMedia: true`, so it
  spans the full width above the question instead of shrinking beside it.
- Data feeds used in exercises: every product of the same group (the
  parent and its variants) has the same price, sale_price and
  availability.
- VERIFY:
  - `node -c` the data file.
  - Text diff: strip tags plus `alt=` / `style=` from the old and new file;
    the visible text must be identical.
  - Screenshot every lesson page (every pageBreak sub-page) and every
    exercise step touched, at window widths 1920, 1400 AND 1200, and fix any
    gap. Course pages are capped at 1000px wide (`.main-inner:has(>
    .page-head)` in style.css) so a fixed-px image keeps matching its text
    on wide screens; if a gap remains, first move the figure, then add a
    sentence consistent with the content (e.g. describing what the image
    shows) — never pad with filler.
  - Bump the `?v=` cache version of every edited .js/.css in the section
    .html files.

3. GIFS / ANIMATIONS
--------------------------------------------------------------------------------
- An animated GIF used as a live demo gets a pause/play control, since a
  raw <img> gif can't be paused natively:
    <div class="gif-image">
      <img data-base-src="img/xxx.gif" src="img/xxx.gif" data-action="zoom-image">
      <canvas class="gif-freeze-canvas"></canvas>
      <button class="gif-toggle-btn" data-action="toggle-gif" aria-label="Pause animation">...</button>
      <p class="example-caption">...zoom badge...</p>
    </div>
  Pausing freezes the current frame on a canvas; resuming can only restart
  the gif from its first frame (a real technical limitation of <img> gifs —
  don't try to fake a resume-from-pause-point).
- A gif that should read as a full-width demo (not squeezed beside text)
  uses `.gif-preview.gif-preview-stacked` (image full width, text below).

4. LABELS / BADGES
--------------------------------------------------------------------------------
- Any short "which one is this" identifier over an image (Option A/B/C,
  Data feed 1/2/3, "Spanish data feed"...) is an ORANGE PILL overlaid on
  the image's top-left corner — never plain heading text above the image:
    background: var(--accent); color: #fff; font-size: 10px; font-weight: 700;
    text-transform: uppercase; letter-spacing: .4px; padding: 3px 8px;
    border-radius: 20px; box-shadow: 0 1px 4px rgba(0,0,0,.35);
  (`.image-choice-caption` and `.feed-preview-label` both use this exact
  style — keep them identical if a third case ever needs it.)

5. ANSWER BUTTONS (quiz-style "choice" fields inside a final exercise)
--------------------------------------------------------------------------------
- Default layout is a wrapping row (`.choice-grid`).
- Switch to `layout: "column"` on the field definition whenever the option
  text is a full descriptive sentence rather than a short label — stacked,
  full-width, left-aligned buttons read much better than a wrapped row of
  long pills. This applies to both `type: "choice"` and `type: "image-select"`
  fields (both read `field.layout === "column"` in app.js).
- Prefer descriptive option text over cryptic short labels when the
  difference between options is the whole point of the question, e.g.:
  "1 Store & 2 Search Engines — one Store for the whole site, with a
  separate Search Engine for each language" rather than just
  "1 Store & 2 Search Engines".

6. EXERCISE STEP LAYOUT (image/media beside text/fields)
--------------------------------------------------------------------------------
- Whenever a step needs an image (or feed preview, or video) reliably
  beside its text AND its answer fields, use the built-in split system —
  do NOT hand-roll it with CSS floats (floats only work for plain prose,
  not for guaranteeing fields land beside media):
    scenarioImage: { src, alt, imgClass? }   — a single image
    scenarioFeed: { label, src, alt, href, downloadLabel }  — feed preview + download button
    scenarioVideo: { embedUrl }              — an embed (text goes left of it automatically)
    scenario: "..."                          — the side text, next to the media
    fieldsRow: true                          — lays fields side by side instead of stacked, inside the side column
    mediaRight: true                         — flips the order so the image is on the right instead of the left
    smallMedia / mediumMedia: true           — 300px / 420px media column instead of the 620px default
    scenarioImage.imgClass: "taller-scenario-img" — bumps a specific image's height (fixed height + object-fit:
                                                     contain) when its natural aspect ratio leaves it too short
  Floats (`.lesson-figure-left/right`, `float-left` on a carousel) are still
  the right tool for a plain image beside a paragraph of running theory
  text with no interactive fields attached.
- Final-exercise step titles are named after the FEATURE the step works
  on, not after the problem: "3. Boosting", "5. Banners". When a feature
  takes two steps (e.g. diagnose, then configure), both share the number
  and add "— Part 1" / "— Part 2" ("2. Relevance Criteria — Part 1",
  "2. Relevance Criteria — Part 2"). A first step that isn't about a
  single feature (e.g. picking the right feature for each problem) keeps
  a descriptive title.
- The first step of each feature (its "Part 1", or its only step) opens
  with "Quick reminder of what needs fixing: …" — the problem from the
  intro list restated in DIFFERENT words (not copy-pasted) and without
  hinting at the answer. Say it once: if the step already has a note that
  restates the problem (e.g. an image-select `trailingNote`), prefix that
  note instead of adding a second paragraph.
- Each final-exercise step has a numbered title ("4. ...") and the header
  shows both the progress dots AND a plain-language "Step X of N" label
  next to them (`.exercise-stepper` / `.exercise-step-label`).
- A step's `explain` only justifies THAT step's answer. It must never hint
  at how to solve a later step (no "like Availability and Price", no
  "brand = Nike or Adidas", no "can be matched partially" when those are
  exactly what the next steps ask the learner to configure). Keep it to
  what each feature does in general.
- After the final reply message, a primary button leads to the next
  section (e.g. "Go to Module 1 Section 2 →"). It's set per data file with
  `nextSection: { label, href }` at the top of COURSE — a NEW section must
  set it too (the last one points back to the Course Path), and the
  previous last section must be updated to point to the new one.
- Once a final-exercise step is answered, the step stays on screen exactly
  like a quiz question: its options/fields stay visible and locked, the
  correct option is marked green and the learner's wrong pick red (a
  wrong dropdown/text value also shows "Correct answer: …" under it), and
  the explanation appears below with the Continue button. The options
  never disappear behind the explanation (handled in app.js by the
  `locked` render of each phase — no per-step setup needed).
- Every correct-answer feedback line during a quiz shows the points earned
  for that question immediately ("Correct! +N points"), not just a final
  tally at the end of the quiz.

7. TONE / VOICE
--------------------------------------------------------------------------------
- The course is a simulated support case: the learner is Mark Park, a
  junior developer at Doostride (an online footwear/streetwear store),
  reporting to John River (CEO) and Amanda House (ecommerce manager).
  Keep every section's narrative consistent with that framing.
- Theory copy (every lesson's `lead` and `blocks`) is IMPERSONAL — never
  "you"/"your" addressing the learner. Use Doofinder, the feature, the
  Store or a passive/neutral phrasing instead:
    "With Doofinder you can configure..." → "Doofinder makes it possible to configure..."
    "your Search Engine" → "a Search Engine" / "the Search Engine"
    "In this lesson you'll learn..." → "This lesson covers..."
    "you can decide between X or Y" → "X allows choosing between..."
    "Before You Copy" (heading) → "Before Copying"
  "You"/second person is only for the NARRATIVE layer: the intro message
  and its side note, the final-exercise intro and steps, the reply
  message, and quiz/exercise questions that set up a scenario for the
  learner ("You type 'comfort' into Results Preview...").
- The person searching in the store is always the "user" / "users" —
  never "shopper" / "customer".
- Name settings exactly as the Admin Panel labels them, never with a
  generic synonym: Relevance Criteria sort orders are "Highest to lowest" /
  "Lowest to highest" (numeric) and "A to Z" / "Z to A" (text) — NOT
  "ascending/descending". Same for toggles, buttons and options quoted in
  theory or quizzes.
- Explanations for a wrong quiz option should say why it's wrong, not just
  that it is — the `explain` field is a teaching moment, not a scoreboard.
- Keep sentences plain and un-padded — cut generic "best practice" advice
  paragraphs that don't map to a concrete Doofinder mechanic and aren't
  tested anywhere (they read as filler and make the lesson feel longer
  than it needs to be).
- Once a section's overview lesson has established that a set of features
  are Search Engine-level configuration (e.g. "How Doofinder Search Works"
  in Section 2 lists Search Fields, Relevance Criteria, Boosting, Custom
  Results, Excluded Results, Synonyms as "the Search Engine's own
  configuration"), don't restate that framing in every later lesson that
  covers one of those features individually — it's already established.
- Don't spell out a feature's Admin Panel navigation path in theory prose
  (e.g. "It's configured from the Admin Panel, under Configuration →
  Excluded Results, on the Search Engine you want to affect") — the
  lesson's own screenshot already shows where it lives. This applies to
  the general "here's where you find it" sentence, not to an actual
  in-screen click sequence that's part of a step-by-step instruction
  (e.g. "click 'Add results' → 'Individual items'" is fine — it's telling
  the learner what to click, not restating a location already visible in
  the image). Quiz questions like "Where is X configured?" are unaffected —
  they test recall of what the screenshot showed, they just don't need a
  matching sentence in the theory copy above it.

8. CREATING A NEW SECTION FROM SCRATCH
--------------------------------------------------------------------------------
This is the whole workflow, distilled from building Module 1 Section 3
(Excluded Results, Grouping Product Variants, Synonyms, Redirections,
Banners, Copy Settings) on top of Sections 1 & 2. To commission a new
section, you only need to hand over TWO things:
  1. The list of lesson topics, each with its support.doofinder.com URL
     (docUrl, plus extraDocs for any named subtopic that has its own page).
  2. A short narrative hint: who is messaging whom, on which platform
     (WhatsApp / Slack / email), and roughly what's being asked for. One
     sentence per topic is enough — e.g. "banners: we need something for
     Black Friday" — everything else below is inferred from that.
Everything else — persona continuity, file structure, quiz writing, image
placeholders, and the final exercise — is derived automatically using the
rules below.

- FILE STRUCTURE (one data-sectionN.js, mirrors Sections 1 & 2 exactly):
    id 0: "Recap: Section N-1" — hasQuiz:false, pages:[{intro, schema}],
          a plain <ul> summarizing the previous section's lessons.
    id 1: "Introduction" — hasQuiz:false, pages:[{intro:[], <platform>: {...},
          <platform>Note:[...]}], see NARRATIVE below.
    id 2..N-1: one lesson per topic — hasQuiz:true, theory:{lead, blocks:[...]},
          quiz:[...]. See THEORY BLOCKS and QUIZZES below.
    id N: "Final Exercise" — hasQuiz:true, quizLabel:"Guided Exercise",
          exerciseType:"wizard", theory:{...} (short recap list) plus
          exercise:{lead, doneNote, replyButtonLabel, phases:[...], reply<Platform>}.
          See FINAL EXERCISE below.

- PERSONA CONTINUITY: keep reusing Doostride and its cast (Mark Park,
  John River, Amanda House, and now Samanta) unless told otherwise — a new
  section is a new chapter in the same running story, not a new company.
  Whoever is named in the narrative hint as "asking" becomes the message
  sender; whoever is named as the learner becomes "you" for that section's
  intro/outro copy (this can rotate — Section 1 was Mark, Section 2 was
  Amanda, Section 3 is Samanta).

- NARRATIVE (id 1 "Introduction"): reuse the existing whatsapp/whatsappNote
  fields for a WhatsApp-style intro (`renderWhatsappCard` in app.js), or the
  slack/slackNote fields for a Slack-style one (`renderSlackCard`) — pick
  whichever platform the narrative hint names; an email variant also exists
  (`email` field) for a more formal ask. The message body is a numbered list
  of complaints/asks, ONE PER LESSON TOPIC IN THIS SECTION, in the same
  order the lessons will be taught — this list is what the final exercise
  will resolve, one phase per line. The side note (`*Note`) is 3-4 short
  paragraphs: (1) who "you" are this section and your relationship to the
  sender, (2) "this morning you got this message from X", (3) the list of
  new features you're about to learn, (4) the explicit promise that the
  final exercise will let you fix everything just asked for.

- THEORY BLOCKS (per lesson): convert the linked support-doc content into
  `theory: { lead, blocks: [...] }`, following ALL the rules already in this
  guide (section 1: merge headless blocks; pageBreak only for a real named
  subtopic; section 1b: h3 sub-topics, tables, callouts, floating images;
  section 2: one figure per subtopic sized to match the text beside it;
  section 7: keep the tone plain, cut generic filler). Do not
  invent product behavior — only reformat and illustrate what the doc
  (or previously verified lesson content) actually says.

- QUIZZES: 6-9 questions per lesson, one correct answer each, an `explain`
  that teaches (not just confirms), covering: the feature's core definition,
  where it's configured, its limits/maximums, and 2-3 of its trickier rules
  or edge cases (the kind of thing a quiz should actually catch someone on).
  If a lesson already has a verified quiz from an earlier draft, keep it —
  don't rewrite working questions just to rewrite them.
  The correct answer must NOT sit mostly in the same position: spread
  `correct` evenly across 0/1/2/3 within each lesson and across the whole
  section (shuffle the options, then set `correct` to the answer's new
  index — and double-check options[correct] is still the right answer).
  When a lesson has a sub-page (e.g. "Stemming and Character Cleaning"),
  its quiz covers both pages — at least one question per sub-topic.
  Avoid two questions with the same answer (e.g. two that both resolve to
  "fuzzy"); test different concepts instead.
- WORKED EXAMPLES: whenever a lesson explains a mechanic that produces a
  result (a score, an order, a match / no match), add a small worked example
  right after the rule — usually a theory-table with generic products and
  their numbers (e.g. Boosting: Product | Boosting | Final score | Position;
  Relevance Criteria: the same four products sorted by two different
  configurations; Search Fields: the same query under two weight setups).
  Mark made-up scores as "simplified numbers, for illustration only" when
  they don't reflect how Doofinder really computes them.
- QUIZ = ONLY WHAT THE LESSON TEACHES: every question (and its correct
  answer and `explain`) must be answerable from the lesson's own theory.
  If a fact isn't in the lesson (e.g. the valid range of df_manual_boost),
  don't ask about it — replace the question with one on something the
  lesson does cover, rather than adding the fact to the theory just to
  justify the question.
- EXAMPLE-BASED QUIZ QUESTIONS: for every worked example in the theory,
  add at least one quiz question that checks the learner understood it,
  built on a DIFFERENT example (other products, other fields, other numbers)
  — never the same example copied from the theory, so it tests the rule and
  not memory. E.g. theory uses "boots" with Relevance 4 vs 2 × 1.5; the quiz
  uses "sandals" with 6 vs 3 × 1.5. The `explain` walks through the maths.

- NO HINTS IN THE ASK: the intro message (and the exercise's own task
  lists) describe each PROBLEM and the desired outcome only — never the
  feature that solves it ("there's nothing in the search pointing people
  to the campaign page", not "we don't have a banner"). The final exercise
  then has a "Picking the right feature for each problem" step (a select
  per problem, options = the section's features in alphabetical order)
  before the per-feature steps, as in Sections 2 and 3.
- FINAL EXERCISE: one phase per lesson topic, in the same order as the
  intro's complaint list, using only the established field types (select,
  choice, text with freeform:true, image-select, multi-choice) — never
  invent a new field type.
  `multi-choice` = a row of toggle buttons where the learner switches on
  EVERY right option (correct: an array), then clicks Continue. Use it
  instead of a column of "Not used / value" dropdowns whenever the task is
  "which of these fields/items belong here?" — e.g. "Relevance Criteria —
  which fields to add", listing all the indexed fields as buttons.
  The buttons show FIELD NAMES only (brand, category…), never "field:
  value" pairs — the values are worked out in the "Part 2" step. The
  Part 1 question describes the problem in general terms (what's wrong and
  what the goal is), without replaying a specific search or product, and
  its `explain` doesn't reveal the values either. Grouping/diagnostic topics that need two steps (e.g. "why isn't X
  working" before "fix X") get two phases; everything else gets one. End
  with `doneNote` (a one-sentence "state of the store now" recap) and
  `replyButtonLabel` (e.g. "Reply to Amanda") — NEVER leave these two
  unset for a new section, they are not auto-generated and default to
  blank/"Reply". Close with a `reply<Platform>` matching the intro's
  platform, written as the learner reporting back what got fixed, one line
  per topic.

- IMAGES: every figure and scenario image is a real <img> tag with a fully
  descriptive alt attribute, exactly as if the screenshot already existed —
  never a text placeholder in the copy itself. Since these screenshots
  don't exist yet, at the end of the work, hand over one table: filename,
  and one sentence describing exactly what it should show (this is the
  only manual step left for a new section — everything else in this
  workflow is self-contained).
  PREFERRED SOURCE — the lesson's own support article: before leaving a
  placeholder, check the images on the lesson's `docUrl` page
  (support.doofinder.com). Download the ones that illustrate the lesson
  (the feature's form, a rule pop-up, a worked example and its result in
  the Search Layer), save them under img/ with a descriptive name, LOOK at
  each one, and write the alt + the text beside it from what the image
  actually shows (the article's text and its screenshots don't always
  match — e.g. the Custom Results "Learn By Example" text talks about Lego
  while the screenshots show sunglasses; describe the screenshot).
  EXCEPTION — tabular/data content (a feed preview, a CSV comparison):
  generate this yourself as a real PNG (a simple rendered table, see the
  Python/PIL snippet used for the Section 3 grouping-feed previews) plus
  a real downloadable file under feeds/. These don't require a real Admin
  Panel screenshot, so there's no reason to leave them as placeholders.

- VERIFY BEFORE HANDING BACK: `node -c` every edited .js file; then use a
  small throwaway HTML harness (load the section's data file + app.js,
  force `runtime.sectionId`/`coursePage`/exercise stage, call `renderMain()`)
  with a headless Chrome screenshot to actually look at: the intro card,
  one lesson with a pageBreak, one quiz page, every final-exercise phase
  type used (choice/select/text/image-select), the done screen, and the
  reply screen. Delete the harness file and screenshots when done — they're
  scratch, not part of the site.
